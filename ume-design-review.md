## 1. Summary

The current UME design is a strong starting point and already follows the main idea of a Data Fabric envelope: every record has a common set of fields, a schema for type-specific data, links to related records, a security label, and stable identifiers that can work even when systems are disconnected.

The main areas I would change are:

- **Keep the envelope generic.** Some track-specific fields are currently part of the common envelope. These should move into the payload so the same envelope can support many different data types.
- **Improve the time model.** The current design records when data moves through the system, but it does not clearly represent when the real-world event happened or support a start and end time.
- **Use identifiers that work across distributed systems.** Global counters, integer source IDs, and node-local track IDs can create problems when data comes from multiple sites or disconnected nodes.
- **Keep API URLs out of stored data.** URLs can be generated by the API when needed instead of being stored in the record. This keeps the data independent of a particular API or deployment.
- **Make the security model more general.** The classification structure should support different security schemes, define safe behaviour when labels are missing, and explain how labels are handled when new data is created from several sources.

Most of these changes are relatively small now, but would be much harder to make after large amounts of data and many services depend on the current structure.

The later sections show a proposed revised UME structure, a schema catalogue with example `kind` values, and worked examples.

## 2. Design principles reference

The findings in this review are linked back to the Data Fabric design principles originally outlined by Jason, using the codes below.

| Code | Principle | What it means |
|---|---|---|
| **DP1** | Separate data storage from data access | Store data in the format that works best for the platform, and present it in the format that works best for the client. |
| **DP2** | Everything is spatiotemporal | Time is important for all data. If data has a location, it should also be searchable by location. |
| **DP3** | Distributed by design | The platform should work across edge, site, and cloud nodes, with configurable synchronization between them. |
| **DP4** | Open architecture with standards support | Use open standards for APIs, formats, and protocols so other systems can integrate without major changes. |
| **DP5** | Designed for redundancy and recovery | Data should be replicated where needed, and the platform should recover quickly after failures. |
| **DP6** | Bring your own data model and ontology | Different data types can use their own schemas and models instead of being forced into one common domain model. |
| **DP7** | Provenance, lineage and versioning built-in | The platform should record where data came from, what it was derived from, and how it changed over time. |
| **DP8** | Zero-trust security | Every access should be authenticated and authorized, using least privilege and encryption by default. |

The DP2 description above is my proposed reading of "everything is spatiotemporal": every record has a time, but only records with a meaningful location have geometry (see S2). This should be confirmed with Jason, since it narrows the principle as originally written.

## 3. The envelope concept

The review is based on one main idea: every UME record is made up of two parts.

- **Envelope** — a small, common set of fields that is used for every type of data.
- **Payload** — the type-specific data. Its structure depends on the `kind` and is defined by a registered schema.

This keeps the platform consistent while still allowing different data types to have their own structure.

### 3.1 A simple analogy

Think of a postal envelope.

The outside of the envelope always contains familiar information such as the destination address, return address, postmark, and possibly a security marking. The postal system can sort, route, track, and deliver the letter without needing to understand what is inside.

The Data Fabric works in a similar way.

Common platform services can use the UME envelope to:

- store and route records
- synchronize data between nodes
- apply security rules
- track where data came from
- query by time and location

Only services that understand a specific `kind` need to read the payload.

### 3.2 What belongs in the envelope

The envelope should only contain information that is useful across many different kinds of data.

| Field | Why it belongs in the envelope | Principles |
|---|---|---|
| Record ID | Gives each record a unique identity and allows other records to reference it. | DP3, DP7 |
| `kind` and `schema` | Identify what type of record it is and which schema should be used to validate the payload. | DP6 |
| `entity_id` | Groups records that belong to the same real-world thing, such as a track, alert, sensor, or zone. | DP7 |
| Time | Records when something happened or the time period when it applies. Supports ordering, time-based queries, and retention. | DP2 |
| Geometry | Stores the location or shape when the record has a spatial component. Supports maps and spatial queries. | DP2 |
| Height / volume | Adds vertical information where needed. Points and lines can use a height coordinate, while volumes use a 2D polygon footprint with a `vertical_extent` (lower and upper height limits) on the geometry. | DP2 |
| Source, node, and source event ID | Identify where the data came from and help with routing, synchronization, trust, and duplicate detection. | DP3, DP5, DP8 |
| Provenance | Records what the data was derived from and which service or process created it. | DP7 |
| Security label | Provides the information needed to make access and sharing decisions. | DP8 |
| Links and assets | Reference related services, files, or other resources without putting the file contents directly in the envelope. | DP1, DP7 |

The key rule is that **type-specific fields should stay in the payload**. The envelope should only contain information that the wider Data Fabric needs to handle records in a consistent way.

### 3.3 What belongs in the payload

The payload contains the fields that are specific to a particular `kind`.

For example:

- a track might include callsign, speed, heading, and classification
- an image might include resolution, sensor details, and spectral bands
- an alert might include the rule that triggered it, severity, and status

These fields do not belong in the common envelope because they are not needed by every type of record.

To add a new data type, the platform should only need a new payload schema and type definition in the schema catalogue. The common UME envelope does not need to change.

## 4. What works well

The current UME design already has several good features that should be kept.

| Strength | Why it is useful | Principles |
|---|---|---|
| Common envelope | Gives every record the same basic structure while still allowing each data type to have its own payload. | DP6 |
| Multiple timestamps | Helps measure latency and shows when data was created, sent, received, and stored. | DP2, DP5 |
| Standard links | Uses familiar link types such as `enclosure`, `preview`, `alternate`, and `service` to connect records to related resources. | DP1, DP4 |
| Lineage links | `derivedfrom` shows which records were used to create another record, such as several detections contributing to a fused track. | DP7 |
| URN identifiers | Gives records stable identifiers that do not depend on a network address or connection. | DP3, DP4 |
| Local CRS support | PROJ/GDAL can resolve coordinate systems locally without depending on an external service. | DP3 |
| Security label on every record | Provides a consistent place to store classification and sharing information. | DP8 |
| Integrity checking | `sha256` can be used to confirm that data or files have not been changed. | DP7, DP8 |
| GeoJSON geometry | Uses a common and widely supported format for representing location and shape. | DP2, DP4 |

## 5. Priority findings

The following are the main issues I found in the current UME design. None of these are critical, but fixing them would make the design clearer, easier to maintain, and easier to use across different data types and distributed sites.

| ID | Finding | Suggested change |
|---|---|---|
| **PF1** | Track-specific fields such as `spatial.track` are part of the common UME structure, even though most other data types do not need them. | Move track-specific fields into the track payload. Tracks can still be a standard UME type, but they should not be built into the common envelope. |
| **PF2** | Raw binary track data can be stored as base64 inside the UME record. This makes the record larger and can create a lot of extra data at normal sensor update rates. | Avoid storing raw binary directly in UME records where possible. Send it on the messaging backbone or store it separately as a file or short-retention raw-data record when it needs to be kept. |
| **PF3** | The current time fields do not clearly separate when the real-world event happened from when the data was sent, received, or stored. There is also no common way to show a start and end time. | Add `datetime` for when an event happened and `start_datetime` / `end_datetime` for things that last over a period of time. Keep the processing timestamps together in a separate `times` section. |
| **PF4** | Height can be interpreted differently depending on the CRS and `altitude_type`. This makes it harder for clients to know exactly what the third coordinate means. | Use one consistent height model for UME geometry. Store 3D positions as longitude, latitude, and WGS-84 ellipsoidal height. Keep source values such as pressure altitude in the payload. Represent volumes as a 2D polygon footprint whose geometry carries a `vertical_extent` with lower and upper height limits. State the CRS on every record in `coordRefSys`. |
| **PF5** | The `index` field is a single increasing number across UME records. This requires coordination between nodes and can be difficult when sites are disconnected. | Remove the global counter and use globally unique record IDs such as UUIDv7. Use a separate source event ID to detect duplicate source messages. |
| **PF6** | The current UME JSON structure is close to GeoJSON, but still uses its own custom structure. This makes geometry handling and conversion less straightforward than it needs to be. | Follow GeoJSON practice without requiring the UME to be GeoJSON: use an `id` / `geometry` / `properties` layout, standard GeoJSON geometry objects, and an explicit `coordRefSys`. The UME is internal storage. Downstream services convert records to GeoJSON (or OGC JSON-FG, for example a Prism for volumes) for visualization. |

## 6. Detailed findings

Each subsection has a summary table, then short notes on why each change matters and how to do it.

### 6.1 Temporal

The current UME design already records several useful processing times. The main issue is that it does not clearly separate **when something happened** from **when the data moved through the platform**.

| ID | Finding | Suggested change |
|---|---|---|
| **T1** | There is no single field that clearly means “when the real-world event happened.” `sourced_at` can mean either when the source received the data or when it produced it. | Add `datetime` as the main event or observation time. Keep `sourced_at` for the source processing time. |
| **T2** | There is no common way to represent data that applies over a period of time, such as a video segment, zone, outage, or UTM volume. | Add `start_datetime` and `end_datetime` for records that have a time range. |
| **T3** | `observed_at` currently means when the ingestion platform received the data. The name can be confused with the time the real-world event was observed. | Rename it to `received_at` so its meaning is clear. |
| **T4** | `broadcasted` means when the source sent the data, but the name is more specific than needed. | Rename it to `sent_at`, which works for any transport or protocol. |
| **T5** | `valid_until` can be used for both data validity and storage retention. These are different concepts. | Use `end_datetime` for when the data stops being valid. Handle normal retention by `kind`, and use `expires_at` only when an individual record needs its own expiry time. |

The processing times can then be grouped together under `times`:

```json
"datetime": "2026-09-23T17:46:01.200Z",
"times": {
  "source_at": "2026-09-23T17:46:01.205Z",
  "sent_at": "2026-09-23T17:46:01.210Z",
  "received_at": "2026-09-23T17:46:01.215Z",
  "stored_at": "2026-09-23T17:46:01.230Z"
}
```

This keeps the difference clear:

- `datetime` = when the event happened
- `source_at` = when the source received or produced the data
- `sent_at` = when the source sent it
- `received_at` = when the platform received it
- `stored_at` = when it was written to storage

### 6.2 Spatial

The current UME design already supports GeoJSON geometry and different coordinate systems. The main area to improve is making sure location, height, confidence, and domain mean the same thing across all `kind` values. The current design defines geometry as longitude, latitude, altitude and also uses separate CRS and `altitude_type` fields.

| ID | Finding | Suggested change |
|---|---|---|
| **S1** | Height can be interpreted differently depending on the CRS and `altitude_type`. A client may need to check several fields before it knows what the third coordinate means. | Use one consistent vertical model. Store 3D positions as longitude, latitude, and WGS-84 ellipsoidal height. Keep source-specific values such as pressure altitude in the payload. Represent volumes as a 2D polygon footprint whose geometry carries a `vertical_extent` with lower and upper height limits. |
| **S2** | The design allows `spatial` to be `null`, but it does not clearly define which data types require geometry and which do not. | Define the geometry rules for each `kind`: `required`, `optional`, or `forbidden`. This avoids adding made-up locations to records that do not have a meaningful position. |
| **S3** | Raw sensor data may not yet contain a known target position. Using a target point before the message is parsed could make spatial queries misleading. | If the target position is unknown, use the sensor location or sensor coverage area when useful, and clearly identify where the geometry came from with `geometry_source`. |
| **S4** | `confidence` is a value from `0.0` to `1.0`, but the design does not define exactly what that number means. | Use a clearly defined field such as `position_error_m` for position accuracy. If other confidence values are needed, keep them in the payload and define their meaning in the payload schema. |
| **S5** | `domain` mixes physical operating areas such as `AIR`, `LAND`, and `SPACE` with categories such as `CYBER`, `ENVIRONMENTAL`, and `LOGISTICS`. | Decide what `domain` is intended to represent and keep the list consistent. If it represents physical operating domains, keep other categories in the payload or another field. |
| **S6** | Fields such as `horizontal_speed`, `vertical_speed`, and `bearing` do not clearly state their units or reference. | Include units and meaning in the field names, for example `ground_speed_mps`, `vertical_rate_mps`, `course_deg`, or `heading_deg`. |
| **S7** | `track_id` is an integer, but the design does not define whether it must be unique across all nodes or only within one source or site. | Namespace track IDs so they remain unique when data from different nodes is combined, for example `site-a:9421`. |
| **S8** | GeoJSON Polygon can describe an area or surface, but it does not directly describe an airspace volume with both a lower and upper height. | For volumetric data such as UTM volumes, NOTAMs, and geofences, store the 2D footprint once as the `geometry` polygon and add the height limits to it as `vertical_extent` (`lower`, `upper`). This keeps one shape per record, with its heights attached. A JSON-FG Prism can be derived from these at the API edge if a client needs one. |

For geometry, I would also add a small `geometry_source` field so clients know where the location came from.

For example:

```json
"geometry_source": "observed"
```

Possible values could include:

- `observed` — the position came directly from the data
- `defined` — the area was explicitly defined, such as a zone or UTM volume
- `sensor_coverage` — the geometry represents the sensor coverage area
- `sensor` — the geometry is the sensor location
- `aoi` — the geometry is a mission area of interest

This makes it clear whether the geometry represents the actual object position, a defined area, or a sensor's location or coverage.

There is deliberately no fallback to the processing node's location. A record with no meaningful location should have `geometry: null` (and `geometry_source: null`).

### 6.3 Links

The current UME design already provides a useful way to link records to files, services, and other records. The main improvement is to clearly separate **identity**, **storage location**, and **client access**.

| ID | Finding | Suggested change |
|---|---|---|
| **L1** | Some links, such as `self` and preview URLs, are API-specific paths stored directly in the UME. These paths may change between deployments or APIs. | Store stable identifiers and references in the UME. Generate client-facing URLs when the record is returned through an API. |
| **L2** | `next` and `previous` may not be known when a record is first created. Adding them later would require changing an existing record. | Calculate `next` and `previous` when the data is queried or returned to a client. |
| **L3** | `derivedfrom` provides useful lineage, but finding all records that were created from a specific record may require searching through many link arrays. | Keep lineage in the UME, but consider an indexed database table for faster reverse-lineage searches. |
| **L4** | `derivedfrom` is a custom link name, and lineage, files, and service links all share the same `links` array. | Give each relationship one home: lineage in `provenance.derived_from`, files in `assets`, and only service or related-resource links in `links`, using IANA relation names (`service`, `related`, `alternate`, `describedby`). |
| **L5** | `length` is included on every link, even when the link does not point to a file. | Make `length` optional and keep file size with the asset where it has a clear meaning. |

#### IDs, references, and URLs

An important part of the design is the difference between **identifying something** and **locating or accessing it**.

- `id` identifies the UME record itself.
- A `derived_from` URN identifies another UME record.
- An asset `href` tells the platform where a related file is stored.
- A `self` URL tells a client how to access a record through a particular API.

For example:

```json
"id": "urn:uuid:01926f3a-8e10-7c32-b7e1-8890cf2b6941"
```

This identifies a specific UME record. It does not mean that the record is stored at that location.

The platform can use the ID to find the record wherever it is stored, for example in PostgreSQL, an archive, or another node.

A relationship to another UME uses the same kind of identifier. Lineage is stored once, in `provenance`:

```json
"provenance": {
  "derived_from": [
    "urn:uuid:01926f3a-7d01-7bb2-b841-39659b8120e5"
  ]
}
```

If a UME has a related file, the asset can contain its storage reference:

```json
"assets": {
  "data": {
    "href": "s3://mission-lake/video/rec_01.mp4"
  }
}
```

Client-facing URLs such as:

```text
/collections/tracks/items/<id>
```

can be added by GSS or another API when the record is returned to a client.

A simple way to think about it is:

> **IDs identify things. Asset references locate files. APIs provide access paths.**

This keeps the stored UME independent of a particular database location, API path, hostname, or deployment.

### 6.4 Assets

The current `asset_descriptor` contains several different types of information in one place, including file details, source information, schema information, processing state, and storage state.

The main recommendation is to separate **information about the UME record** from **information about files related to the record**.

| ID | Finding | Suggested change |
|---|---|---|
| **A1** | `asset_descriptor` mixes record information and file information together. | Move record-level fields such as source and schema into the main UME envelope. Keep file-specific information under `assets`. |
| **A2** | The current design does not clearly separate what the data represents, the schema that describes it, and the format of a file. | Use `kind` to describe what the record represents, `schema` to describe the payload structure, and asset `type` to describe the file format. |
| **A3** | `lifecycle` mixes different ideas. `RAW` describes what the data is, while `PROCESSING` and `AVAILABLE` describe its current state. | Use `kind` or the payload to describe the type of data. Keep temporary processing state separate from the historical UME record. |
| **A4** | `lifecycle` and `storage_tier` can change after the UME is written. | Keep changing state outside the UME record, for example in a separate `ume_state` table or storage-management service. |
| **A5** | `source_id` is an integer, but the design does not define whether it is unique across all sites and nodes. | Use a stable identifier per device or producing service, such as `urn:source:flightline-0037`, and record the ingesting node separately in `source.node`. Keeping the site out of the source ID means a sensor that moves between sites keeps the same identity. |
| **A6** | `sha256` is included, but it is not clear exactly what data is being hashed. | Define the checksum as the hash of the exact asset bytes so every service calculates it the same way. Store it as a SHA-256 multihash (`1220` followed by 64 hex characters), the format the STAC File extension uses for `file:checksum`. `config_hash` uses the same format. |
| **A7** | Some checksum values in the examples appear to be placeholders. | Use real or clearly marked example checksum values and validate them as part of the test examples. |
| **A8** | The relationship between the UME ID and asset UUID is not clearly defined. | Only give an asset its own ID when it needs a separate identity, such as when several UME records reference the same file. |
| **A9** | There is no way to recognise the same source event arriving twice, for example when two adapters receive the same sensor message or a node replays data after reconnecting. The record ID cannot do this, because each producer generates its own. | Add `source.event_id`, derived from source-native data (a message ID or a natural key) so every adapter computes the same value. The deduplication key is `(source.id, kind, source.event_id)`. `kind` is included because one source event can produce several records, such as a `track.raw` and a `sensor.detection` from the same ASTERIX report. |

### 6.5 Provenance and versioning

The current UME design already supports basic lineage through `derivedfrom` links. This is a good starting point because it allows one record, such as a fused track, to point back to the records that were used to create it.

The main improvement is to capture more information about **how a record was created and how corrections or operator actions are handled**.

| ID | Finding | Suggested change |
|---|---|---|
| **V1** | The record does not identify the software version or configuration that produced it. | Add fields such as `producer_version` and `config_hash` so the exact producer setup can be traced later. |
| **V2** | `derivedfrom` shows where a record came from, but there is no clear way to say that one record replaces or corrects another. | Add `revision_of` for corrections or replacements of an earlier record. Normal track updates should remain separate observations, not revisions. |
| **V3** | The lineage structure is specific to UME. | Keep the UME structure simple, but consider mapping it to W3C PROV when data needs to be exchanged with systems that use a standard provenance model. |
| **V4** | The design does not define a way to prove that provenance information has not been changed. | Where chain-of-custody or stronger integrity is required, consider signing records or batches at the producer. |

A simple provenance structure could look like:

```json
"provenance": {
  "origin": "urn:source:flightline-0037",
  "derived_from": [
    "urn:uuid:01926f3a-7d01-7bb2-b841-39659b8120e5"
  ],
  "revision_of": null,
  "produced_by": "omnitrack-engine",
  "producer_version": "3.4.1",
  "producer_org": "urn:org:dnd",
  "config_hash": "12209c9c...9c"
}
```

The key difference is:

- `derived_from` = which records were used to create this one
- `revision_of` = which earlier record this one corrects or replaces
- `produced_by` = which service created it
- `producer_org` = which organization produced it (which may differ from the security `originator`, 7.3)
- `producer_version` / `config_hash` = which software and configuration were used (`config_hash` is a SHA-256 multihash, A6)

This makes it easier to understand how a result was produced without changing older records.

### 6.6 Extension fields

The current design has more than one place for type-specific data. There is a general `properties` object and another `properties` object inside `spatial.track`.

This can make it unclear which schema applies to which fields.

| ID | Finding | Suggested change |
|---|---|---|
| **X1** | Type-specific fields can appear in more than one place, such as `properties` and `spatial.track.properties`. | Use one `payload` section for all data that is specific to the `kind`. The schema referenced by the record defines the structure of that payload. |
| **X2** | The design does not define how commonly searched payload fields should be indexed. | Allow each `kind` to provide `index_hints` in its type definition so database tooling can create the needed PostgreSQL indexes. |

For example:

```json
"payload": {
  "track_id": "site-a:9421",
  "callsign": "C-GKSI",
  "ground_speed_mps": 210.5,
  "squawk": "7700"
}
```

The payload schema defines which fields are allowed for that `kind`.

Its `type.yaml` can then suggest indexes for fields that are searched often:

```yaml
index_hints:
  - "payload->>'callsign'"
  - "payload->>'squawk'"
  - "payload->>'target_address'"
```

Database tooling could use those hints to create indexes such as:

```sql
CREATE INDEX idx_track_fused_squawk
ON ume_records ((payload->>'squawk'))
WHERE kind = 'track.fused';
```

This keeps type-specific fields out of the common envelope while still allowing fast searches.

### 6.7 Storage mapping

The current design maps UME fields into PostgreSQL, while JSON objects and arrays remain stored as JSON rather than becoming individual columns.

This is a reasonable starting point. The main goal should be to keep the database structure stable as more `kind` values are added.

| ID | Finding | Suggested change |
|---|---|---|
| **D1** | As more data types are added, putting type-specific information into common database columns can lead to a large and sparse table. | Store commonly searched envelope fields as normal PostgreSQL/PostGIS columns and keep kind-specific fields in `jsonb` payloads. |
| **D2** | The design does not yet define an indexing approach for common spatial, time, security, and payload queries. | Define a standard set of indexes for envelope fields, and create kind-specific payload indexes from the schema catalogue where needed. |

A database layout could look like:

```text
id              uuid
kind            text
entity_id       text
datetime        timestamptz
start_datetime  timestamptz
end_datetime    timestamptz
geometry        PostGIS geometry
source_id       text
source_node     text
source_event_id text
security        jsonb / columns
provenance      jsonb
payload         jsonb
assets          jsonb
```

Common fields stay easy to query and index, while each `kind` can still define its own payload without requiring a database migration.

Typical indexes could include:

```sql
-- Time queries
CREATE INDEX idx_ume_datetime
ON ume_records (datetime);

-- Spatial queries
CREATE INDEX idx_ume_geometry
ON ume_records
USING GIST (geometry);

-- Kind and time queries
CREATE INDEX idx_ume_kind_datetime
ON ume_records (kind, datetime);

-- Duplicate detection (A9)
CREATE UNIQUE INDEX idx_ume_source_event
ON ume_records (source_id, kind, source_event_id);
```

Additional payload indexes can be created from the `index_hints` defined for each `kind`.

If the table is partitioned by time (for example a TimescaleDB hypertable on `datetime`), unique indexes must include the partition column, so the duplicate-detection index becomes `(source_id, kind, source_event_id, datetime)`. That only catches duplicates if every adapter derives `datetime` the same way for the same event, which the type definition for each `kind` should state.

#### Latest-state view

The UME history is append-only, but operational screens usually need the current state: where each track is now, which alerts are open, the status of each sensor. A small latest-state table (or materialized view) holds the most recent record for each entity, while the full history stays unchanged.

It should be keyed on **`(entity_id, kind)`**, not `entity_id` alone. Several kinds can describe the same entity:

- a `track.fused` update and a `track.command` both refer to the same track
- an `alert.zone_breach` and its `alert.state_change` both refer to the same alert
- several `utm.volume` records and the `utm.intent_state` records all refer to the same operational intent

Keyed on `entity_id` alone, an operator command would replace the track's position, and an acknowledgement would replace the alert itself. Kinds that have several current records per entity (such as the volumes of one operational intent) can add a sub-key in their type definition, for example `payload.volume_index`.

### 6.8 Messaging

The current UME design describes the stored record structure, but it does not fully define how UME records are sent between services.

A clear messaging contract should define how the same logical UME is carried over the messaging backbone.

| ID | Finding | Suggested change |
|---|---|---|
| **M1** | `$schema` is used on the UME record, but the name can be confusing because `$schema` already has a specific meaning in JSON Schema documents. | Use an explicit field such as `ume_version` or an envelope schema reference to identify the UME format. Keep the payload `schema` separate. |
| **M2** | The wire format and messaging metadata are not clearly defined. | Define a standard messaging representation. JSON can be used initially, with CloudEvents as a suggested way to carry common event metadata if needed. |

For example:

```text
UME logical model
      │
      ▼
Messaging representation
      │
      ├── NATS subject for routing
      ├── Event metadata
      └── UME record as the message body
```

With NATS, a subject might look like:

```text
fabric.track.fused.site-a
```

CloudEvents could optionally provide common metadata such as:

```text
type:     track.fused
source:   urn:source:omnitrack-01
time:     2026-09-23T17:46:01.200Z
subject:  urn:track:site-a:9421
```

The complete UME record remains the message body.

It is important to keep the responsibilities separate:

- **NATS subjects or Kafka/MQTT topics** control routing and subscriptions.
- **CloudEvents** can provide a standard way to describe event metadata.
- **UME** defines the actual data model and record contents.

CloudEvents is a suggested implementation option, not a requirement of the UME model.

This allows the same UME logical model to work over different transports without changing the meaning of the data.

## 7. Classification and labelling

### 7.1 Access decisions

A security label is only useful if the platform checks it whenever data is viewed, streamed, exported, or shared.

One suggested way to do this is **Open Policy Agent (OPA)**. OPA is not required by UME, but it provides a common place to apply access-control rules across the platform.

### What OPA does

OPA is a policy engine. A service sends OPA information about the user and the data being requested. OPA applies the configured security rules and returns a decision, such as allow or deny.

```text
Service                                      OPA

"Can this user see this record?"  ─────►   Check policy rules

User attributes
Record security label             ─────►

                                  ◄─────   Allow / Deny
```

For example, a service could provide:

- the user's clearance
- nationality or organization
- any caveats or compartments they hold
- the record's `security` label

OPA then compares them using the rules defined for that security policy.

### Why use a policy engine?

Using a common policy engine avoids putting separate security rules inside every service.

| Benefit | What it means |
|---|---|
| One set of rules | Query APIs, live streams, the BFF, exports, and other services can all use the same security rules. |
| Rules are separate from application code | Security rules can be updated without changing the access-control logic in every service. |
| Easy to test | Policy rules can have their own automated tests. |
| Easier to audit | Access decisions can be logged, including who requested the data and whether access was allowed. |
| Can work offline | Policy rules can be distributed to edge nodes so they can continue making access decisions while disconnected. |
| Can help filter database queries | For large queries, policy rules can be used to help build database filters so PostgreSQL only returns records the user is allowed to access. |

### How it works with identity

The identity system and the policy engine have different jobs.

An identity provider such as Keycloak answers:

> **Who is this user?**

It can provide attributes such as:

- clearance
- nationality
- organization
- caveats or compartments

The policy engine answers:

> **What is this user allowed to see?**

It compares the user's attributes with the record's `security` block and applies the appropriate rules.

This is an example of **Attribute-Based Access Control (ABAC)**.

```text
Identity Provider
      │
      │ User identity and attributes
      ▼
   Service
      │
      ├── User attributes
      └── Record security label
              │
              ▼
        Policy Engine
              │
              ▼
         Allow / Deny
```

### Where access checks happen

Access checks should be made anywhere data can leave the platform or be provided to a user.

Examples include:

- **Query APIs** — filter records returned to the user.
- **Live streams** — check messages before sending them to a connected user.
- **Export gateways** — check data before it is exported.
- **Partner interfaces** — check data before sharing it with another system or organization.
- **Node synchronization** — decide which records are allowed to replicate to another node, including rules based on `releasable_to`.

OPA could run beside these services as a sidecar, or be integrated through another supported deployment model. The important part is that the same policy rules are applied consistently at every enforcement point.


### 7.2 Findings

The current design has a good starting point, but there are a few areas where the security model could be made clearer and more consistent.

| **ID** | **Finding** | **Suggested change** |
|---|---|---|
| C1 | The design is described as role-based, but the stored security fields are based on attributes such as classification and releasability. The actual access model is not clearly defined. | Describe the model as **Attribute-Based Access Control (ABAC)** if access decisions are based on user attributes and record labels. A policy engine such as OPA could be used to apply these rules. |
| C2 | The current model uses a single `nato_classification` field, but different organizations may use different classification schemes. | Use a common security label and let `policy` identify which scheme applies, such as `NATO`, `CAN`, or `CORP`. |
| C3 | There is no defined way to protect the security label from being changed or separated from the data. | Consider alignment with **STANAG 4774** for confidentiality metadata labels and **STANAG 4778** for binding those labels to the data where required. |
| C4 | `need_to_know` is not clearly defined. It currently uses country or client values, which makes it difficult to distinguish from `releasable_to`. | If the intent is to represent extra restrictions, groups, or compartments, rename it to `caveats` and let the security policy define how those values are checked. |
| C5 | The format for country, coalition, or organization identifiers is not defined. | Use a consistent format, such as ISO 3166-1 alpha-3 codes for countries and agreed identifiers for coalitions or organizations. |
| C6 | The current design does not say what happens when a security label is missing or invalid. | Do not release the data unless a valid access decision can be made. |
| C7 | The current model is mainly based around a NATO-style classification field, which makes reuse for other security schemes harder. | Use the same security label structure for military, government, and commercial data, while allowing each `policy` to define its own values and rules. |

### 7.3 Security label structure

UME stores security labels on each record, but it does not decide what those labels mean or how access decisions are made.

For each security `policy`, a separate policy package defines the rules. These rules would be maintained with the security authority and enforced by the platform. **OPA is one suggested tool that could be used to implement and enforce these rules, but it is not required by the UME model.**

The policy package defines things such as:

- which label values are allowed
- which combinations of labels are valid
- how user clearances are compared with data classifications
- who the data can be released to
- how caveats and compartments are handled
- how security labels are determined when data is created from several sources
- how downgrade or sanitization is handled

The UME envelope only makes sure the security label is present and has the correct structure.

Every record uses the same five security fields:

| Field | What it means |
|---|---|
| `policy` | Identifies which security scheme applies, such as `NATO`, `CAN`, or `CORP`. This tells the platform which policy rules to use. |
| `classification` | Identifies the sensitivity level of the data. |
| `releasable_to` | Identifies which countries, coalitions, or organizations are allowed to receive the data. |
| `caveats` | Adds any extra restrictions, groups, or compartments that must be considered before access is allowed. |
| `originator` | Identifies the organization that controls the information and its release. This may be different from the organization that produced the record, which is stored in `provenance.producer_org`. |

Example:

```json
"security": {
  "policy": "CAN",
  "classification": "PROTECTED B",
  "releasable_to": ["CAN"],
  "caveats": ["OPS-INTEL"],
  "originator": "urn:org:dnd"
}
```

The allowed values depend on the selected policy.

| Policy | Example `classification` values | Example `releasable_to` values |
|---|---|---|
| NATO | NATO UNCLASSIFIED, NATO RESTRICTED, NATO CONFIDENTIAL, NATO SECRET, COSMIC TOP SECRET | Countries or coalitions such as FVEY |
| CAN | UNCLASSIFIED, PROTECTED A, PROTECTED B, PROTECTED C, CONFIDENTIAL, SECRET, TOP SECRET | Countries or approved sharing groups |
| CORP | PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED | Organization IDs such as `urn:org:...` |

This keeps the UME record format consistent while allowing different organizations or deployments to apply their own security rules.

## 9. Controlled lists and standards

UME should use existing standards wherever they already provide a good answer.

This section shows which fields come directly from a standard, which ones are based on standards but adapted for UME, and which ones are specific to UME.

**Legend:**

- ✅ **Standard** — directly uses an existing standard
- ◐ **Standards-aligned** — based on a standard, but adapted for UME
- ✖ **Custom** — defined specifically for UME

### 9.1 Envelope

Most of the basic UME envelope uses existing standards for geometry, time, identifiers, and coordinate formats.

| Field | Example / format | Status | Based on |
|---|---|---|---|
| Record layout | `id`, `geometry`, `properties` | ◐ | Modelled on a GeoJSON Feature, but a UME record is not a GeoJSON Feature (no `type` member) |
| Geometry | Point, LineString, Polygon, MultiPolygon, etc. | ✅ | GeoJSON / OGC |
| Coordinates | longitude, latitude, optional height | ✅ | GeoJSON / OGC |
| `coordRefSys` | `http://www.opengis.net/def/crs/OGC/0/CRS84h` | ✅ | OGC CRS URI (as used by JSON-FG / OGC API – Features) |
| `geometry.vertical_extent` | `{ "lower": 45.0, "upper": 165.0 }` on a Polygon / MultiPolygon (metres, in the `coordRefSys` vertical reference) | ◐ | Same lower/upper model as a JSON-FG Prism, without repeating the footprint |
| `vertical_approximate` | `true` / `false` | ✖ | UME |
| `id` | `urn:uuid:<UUIDv7>` | ✅ | UUID / URN standards |
| Date and time | `2026-09-23T17:46:01.200Z` | ✅ | RFC 3339 |
| `ume_version` | `1` | ✖ | UME |
| `kind` | `track.fused`, `video.segment`, etc. | ✖ | UME |
| `schema` | `urn:schema:...` | ◐ | Uses standard URN format, but the namespace is UME-specific |
| `entity_id` | `urn:track:...` | ◐ | Uses standard URN format, but the namespace is UME-specific |
| `source.id` | `urn:source:...` | ◐ | Uses standard URN format, but the namespace is UME-specific |
| `source.event_id` | Depends on the source | ◐ | Usually built from identifiers already provided by the source system |
| `time_source` | `event`, `source_at` | ✖ | UME |
| `geometry_source` | `observed`, `defined`, `sensor_coverage`, `sensor`, `aoi` | ✖ | UME |
| `domain` | AIR, LAND, SEA_SURFACE, SUBSURFACE, SPACE | ◐ | Based on common military domain concepts |
| `position_error_m` | Position error in metres | ◐ | Uses standard SI units; UME defines the exact meaning |

The main idea is that UME does not invent new formats for things like location, time, and identifiers when a suitable standard already exists.

### 9.2 Security labels

UME uses one common security-label structure, but the actual values depend on the selected security policy.

| Field | Example / format | Status | Based on |
|---|---|---|---|
| `policy` | `NATO`, `CAN`, `CORP` | ✖ | UME |
| NATO `classification` | NATO UNCLASSIFIED, NATO SECRET, etc. | ✅ | NATO security markings |
| CAN `classification` | UNCLASSIFIED, PROTECTED B, SECRET, etc. | ✅ | Government of Canada security markings |
| CORP `classification` | PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED | ✖ | Organization-defined |
| NATO/CAN `releasable_to` | `CAN`, `USA`, `GBR`, `FVEY`, etc. | ◐ | Country codes plus agreed coalition names |
| CORP `releasable_to` | `urn:org:...` | ◐ | Uses standard URN format |
| `caveats` | Extra restrictions or compartments | ✖ | Defined by the selected security policy |
| `originator` | `urn:org:...` | ◐ | Uses standard URN format |

The UME defines **where security information is stored**. The selected policy defines **what the values mean and who is allowed to see the data**.

### 9.3 Links and assets

UME should also use standard link names, media types, and file metadata where possible.

| Field | Example / format | Status | Based on |
|---|---|---|---|
| Stored link `rel` | `service`, `related`, `alternate`, `describedby` | ✅ | IANA Link Relations |
| Generated link `rel` | `self`, `next`, `prev`, `predecessor-version`, `derived_from` | ✅ | IANA / STAC |
| Link or asset `type` | `image/tiff`, `video/mp2t` | ✅ | Standard media types |
| `urn:` reference | `urn:uuid:...` | ✅ | URN standard |
| `s3:` reference | `s3://bucket/file` | ◐ | Common storage format, but not an Internet standard |
| `lake:` reference | `lake://...` | ✖ | Platform-specific |
| Asset `roles` | `data`, `thumbnail`, `alternate`, `metadata` | ✅ | STAC |
| `file:size` | File size in bytes | ✅ | STAC File extension |
| `file:checksum` | File checksum | ✅ | STAC File extension / SHA-256 |
| `config_hash` | Configuration checksum | ✅ | SHA-256 |

The goal is not to make every field come from an external standard.

Fields such as `kind`, `time_source`, and `geometry_source` are specific to UME and that is fine. The important thing is to use existing standards where they fit and clearly document the fields that UME defines itself.

### 9.4 Identifier conventions

UME identifiers are URNs (RFC 8141) of the form `urn:<type>:<id>`. The URNs in this review and in the example records, such as `urn:track:site-a:9421` or `urn:zone:northgrid:substation-b`, are **illustrative**. They show the pattern, not a fixed or registered set.

The platform should define and publish the actual namespaces. Each identifier type should state:

- **Structure:** its segments, for example `urn:schema:<domain>:<name>:v<N>`.
- **Uniqueness scope:** what it must be unique within. Include enough in the ID to make it globally unique. For example, a NOTAM number is only unique per issuing office, so the ID should include the location indicator.
- **Who assigns it:** the source, an adapter, or the platform.

Two points to settle before v1:

- **Namespace ownership.** Names such as `urn:track:` are not registered URN namespaces. That is fine internally, but they could clash if records are shared with partners. Placing all types under one controlled namespace, such as `urn:<org-ns>:track:...`, avoids this.
- **Schema enforcement.** Each identifier type should have a matching pattern in the schemas. Today only `uuid`, `org`, `user` and `source` are checked strictly.

## 10. Schema catalogue

One recommendation is to define a schema catalogue for UME data. I’ve included an example structure in this repository to show how that catalogue could be organized.

For each `kind`, the catalogue would include:

- a **payload schema** that defines what the data should look like
- a **type definition** that describes how UME handles that kind
- at least one **example** showing a valid record

Together, these provide a clear contract for each `kind`. This allows UME to support different data models while still giving the platform enough information to validate the data, index and search it, document it, and manage changes over time.

### 10.1 Schema rules

My idea for the catalogue is to follow a small set of rules that keep the schemas consistent, easy to understand, and manageable over time.

| Rule | What it means |
|---|---|
| Every `kind` must have a schema | UME should always know what a valid payload looks like. Experimental kinds can use a more flexible `draft` schema, but they still need one. |
| Each schema version is separate | The record's `schema` field identifies exactly which schema version it uses, such as `...:v1` or `...:v2`. |
| Small changes can keep the same version | Adding a new optional field does not normally break existing users, so the version can stay the same. |
| Breaking changes need a new version | Removing a field, renaming it, changing its type, or changing what it means requires a new schema version. |
| Old schema versions are kept | Historical records may still use older versions, so those schemas must remain available. |
| Common fields are defined once | Shared definitions such as altitude, angles, speeds, IDs, and standard value lists live in `common.v1` and are reused with `$ref`. |
| Related kinds can share a base schema | Common structures used by a group of kinds, such as alerts, live under `base/` so they do not need to be repeated. |
| Every `kind` has a type definition | The type definition contains rules specific to that kind, such as envelope requirements, how IDs are created, and which fields may be indexed. |
| Every `kind` has examples | Examples show what valid data looks like and are checked automatically in CI whenever the schemas change. |


### Why this matters

These rules give UME flexibility without allowing every producer to define data differently.

A producer can introduce a new payload type, but the platform still knows:

- what fields are expected
- which schema version the record follows
- how the record should be identified
- which fields can be indexed
- how older records should continue to be read

This is what makes the "bring your own data model" approach manageable as the number of `kind` values grows.

### 10.2 Layout

```
schemas/
  ume.schema.json                 envelope (JSON profile)
  common.v1.schema.json           shared definitions
  base/alert.v1.schema.json       base for alerts
  kinds/<kind>/
    v1.schema.json                payload schema
    type.yaml                     type definition
    examples/*.json               valid records (test fixtures)
tools/
  validate.py                     validates everything; used in CI
```

Schemas reference each other by URN (for example `urn:schema:fabric:common:v1#/$defs/altitude`), resolved from this folder, never from the network.

### 10.3 Type definition

Each `kind` has a `type.yaml` file that describes how UME should handle that kind, in addition to defining its payload schema.

The example below shows what a `type.yaml` file could look like for fused track data.

```yaml
# Unique name for this type of UME record
kind: track.fused

# Payload schema that defines the track-specific data
schema: urn:schema:tracks:fused-kinematics:v1

# Indicates whether this type definition is still being developed
status: draft

# Rules that apply to the common UME envelope
envelope:

  # This record represents one point in time rather than a time range
  time: instant                    # instant | span

  # A fused track must include geometry
  geometry: required               # required | optional | forbidden

  # The geometry represents an observed position
  geometry_source: [observed]      # allowed geometry source values

  # Height may be included as the third coordinate: [lon, lat, height]
  z: optional                      # required | optional | forbidden

  # Fused tracks are not volumes, so they have no vertical extent
  vertical_extent: forbidden       # required | optional | forbidden

  # The record must identify the track it belongs to
  entity_id: required              # required | optional | forbidden

  # Defines how the track entity ID is created from the payload
  entity_id_template: urn:track:{payload.track_id}

  # This kind does not require any attached files
  required_assets: []

# Defines how to identify the original source event.
# This helps detect duplicate updates from the source.
source_event_id: track_id + Trackgen update sequence

# Suggested database indexes for common searches.
# Spatial fields would normally use PostGIS indexes,
# while payload fields use PostgreSQL expression indexes.
index_hints:
  - "payload->>'callsign'"
  - "payload->>'squawk'"
  - "payload->>'target_address'"
```

### 10.4 Kinds

These are only example `kind` values, created to show how UME could work with different types of real-world payloads. They are not a fixed or complete list. The table also shows the basic characteristics of each example, including what it represents, whether it applies to a single point in time or a time period, what location or shape it uses, whether height is needed, what entity it belongs to, and whether it includes any related files.

| Kind | What it represents | Time | Location / shape | Height | Linked entity | Files |
|---|---|---|---|---|---|---|
| `track.raw` | One raw message from a sensor | Single point in time | Sensor coverage area | — | — | Batch file |
| `sensor.detection` | One detection from a sensor before tracks are combined | Single point in time | Estimated position | Optional | Optional | — |
| `track.fused` | The latest state of a fused track | Single point in time | Track position | Optional | Track | — |
| `track.command` | An operator action applied to a track | Single point in time | Optional | — | Target track, if needed | — |
| `alert.zone_breach` | An alert when a track enters, leaves, or stays too long in a zone | Single point in time | Where the breach happened | Optional | Alert | — |

## 11. Example UME use cases

The following examples show how the proposed UME structure could represent different types of real-world data.

They are examples only and are not meant to define the final list of UME `kind` values.

Each `kind` has an example under:

```text
kinds/<kind>/examples/
```

The examples are linked together to show how source data, derived data, alerts, state changes, and operator actions can relate to one another.

```text
track.raw ────────┐
                  ├─► track.fused
sensor.detection ─┘

zone.geofence ─► alert.zone_breach ─► alert.state_change
                        └────────────► track.command

utm.volume ─┬─► alert.nonconformance
            └── utm.intent_state
```

The main idea is that each UME record represents one event, observation, state change, or defined object. Related records are connected using identifiers and provenance rather than putting everything into one large record.

### 11.1 Fused track and its inputs

`track.fused/examples/fused-air-track.json` is the fused-track example shown in Section 8.

It shows how data from several sources can be combined into a new track observation.

- **Position** — stored as a 3D point: `[-75.6972, 45.4215, 3200.5]`. The third value is height above the WGS-84 ellipsoid.
- **Track identity** — `urn:track:site-a:9421` identifies the track. Every update for this track uses the same `entity_id`.
- **Source** — `urn:source:omnitrack-01` identifies the Trackgen source. The record was received at `site-a`.
- **Source event** — `site-a:9421:118734` identifies this specific update from the source.
- **Provenance** — `derived_from` points to the raw ASTERIX message and radar detection that helped create the fused track.
- **Producer** — `producer_org` identifies DND as the organization that produced the record.
- **Revision** — `revision_of` is `null` because a new track position is a new observation, not a correction to the previous one.
- **Security** — the record uses the CAN security policy and is marked UNCLASSIFIED.

An important distinction is:

> The UME `id` identifies one specific track observation, while `entity_id` identifies the track itself.

This means a moving track can have many UME records over time, all sharing the same `entity_id`.

### 11.2 FMV video segment

`video.segment/examples/uav-eo-segment.json` represents a 10-second segment from a UAV EO camera.

The UME record describes the video segment, while the actual files are referenced through `assets`.

- **Time** — `start_datetime` and `end_datetime` define when the video segment was recorded.
- **Geometry** — the geometry represents the area on the ground visible in the video.
- **Sensor position** — the UAV or camera position is kept separately in the payload.
- **Provenance** — because this is source data, `derived_from` is empty.
- **Derived data** — if a detection is later produced from the video, that `sensor.detection` record can point back to this video segment using `derived_from`.
- **Links** — a `service` link can identify the live video stream. `next` and `previous` do not need to be stored because they can be generated when the data is queried.

The related files are stored as assets:

| Asset | What it contains | Media type |
|---|---|---|
| `data` | Original video segment with KLV | `video/mp2t` |
| `hls` | Playback version | `application/vnd.apple.mpegurl` |
| `thumbnail` | Preview image | `image/jpeg` |
| `klv` | Decoded KLV metadata | `application/json` |

The asset `href` values can use storage references such as:

```text
s3://mission-lake/video/segment-001.ts
```

GSS can turn these into a URL that the client can use after the access check succeeds.

The orthomosaic example under `imagery.ortho` follows the same idea: the UME describes the imagery, while the actual image files are stored as assets.

### 11.3 UTM volume, state and non-conformance

`utm.volume/examples/bvlos-nominal-volume.json` shows how UME could represent a UTM flight volume.

In this example, the volume represents a BVLOS operation west of Ottawa from 18:00 to 18:25, between 45 m and 165 m.

| Concept | How it is represented |
|---|---|
| Flight area | `geometry` contains the 2D footprint. |
| 3D volume | The geometry's `vertical_extent` contains the lower and upper height limits. |
| Active time | `start_datetime` and `end_datetime` define when the volume applies. |
| Operational intent | All records for the same intent share the same `entity_id`. |
| Volume type | `volume_type` identifies the volume as `nominal` or `off_nominal`. |
| Updated volume | A new record is created. `revision_of` can point to the previous version. |
| Intent state | State changes such as Accepted or Activated are stored as separate `utm.intent_state` records. |
| Non-conformance | If a track leaves its allowed volume, an `alert.nonconformance` record is created. |

#### Intent state change

`utm.intent_state/examples/intent-activated.json` shows the intent changing from Accepted to Activated at 18:00.

The record does not need its own geometry because the related `utm.volume` already defines where the operation takes place.

A source event ID such as:

```text
<intent>:v1:Activated
```

can help identify duplicate messages if the same state change is received more than once.

#### Non-conformance

`alert.nonconformance/examples/bvlos-volume-exit.json` shows track `site-a:9512` leaving its allowed flight volume.

The alert points back to both:

- the track that left the volume
- the UTM volume that defined where the aircraft was allowed to operate

Both are referenced through `derived_from`.

This keeps three different concepts separate:

```text
utm.volume
    │
    ├── defines where and when the flight may operate
    │
    ├── utm.intent_state records changes to the intent
    │
    └── alert.nonconformance records a detected problem
```

### 11.4 NOTAM

`aim.notam/examples/ottawa-restricted-area.json` shows how UME could represent a temporary restricted area.

In this example, the NOTAM:

- applies from 17:00 to 21:00
- covers a 2 NM radius
- extends from the surface to 1,500 ft AMSL
- prohibits RPAS operations while active

| Concept | How it is represented |
|---|---|
| Active time | `start_datetime` and `end_datetime` |
| Schedule | Additional schedule information stays in the payload |
| Area | `geometry` contains the area used for spatial searches |
| Height limits | The geometry's `vertical_extent` contains the vertical limits |
| NOTAM details | ID, Q-code, FIR, location, and text stay in the payload |
| NOTAM identity | `entity_id` identifies the NOTAM |
| Replacement | A new record can use `revision_of` to point to the previous NOTAM |
| Original files | AIXM and ICAO-format text can be stored as assets |

The example keeps both:

- a normalized UME representation that the Data Fabric can search
- the original NOTAM information for systems that need the aviation-specific details

This allows common platform services to work with the NOTAM without losing the original source information.

### 11.5 Zone, alert, acknowledgement and command

This Counter-UAS example shows how several UME records can work together to describe a site-protection event.

| Record | What it represents |
|---|---|
| `zone.geofence` | Defines the protected area around Substation B. |
| `alert.zone_breach` | Records that a UAS entered the protected area. |
| `alert.state_change` | Records that an operator acknowledged or changed the state of the alert. |
| `track.command` | Records an operator action against the track, such as reclassifying it. |

The records can be linked like this:

```text
zone.geofence
      │
      │       track.fused
      │           │
      └───────────┴────► alert.zone_breach
                              │
                              ├──► alert.state_change
                              │       acknowledged
                              │
                              └──► track.command
                                      reclassify
```

Each record has a different purpose:

- the **zone** defines the protected area
- the **track** identifies the UAS
- the **alert** records that a breach occurred
- the **state change** records what happened to the alert
- the **command** records what the operator did

This keeps the history clear because each event is stored as its own record instead of repeatedly changing one record.

`sensor.status/examples/rid-receiver-operational.json` adds the Remote ID receiver to the same site picture.

The status record can contain:

- the sensor's operating state
- its coverage area
- its `entity_id`

All status updates for the same sensor use the same `entity_id`. This allows the platform to show the latest sensor status while still keeping the previous status records.

## 12. Vertical model

### Recommendation

Store height as part of the geometry wherever possible.

For points, lines, and other position-based geometry, use the third GeoJSON coordinate:

`[longitude, latitude, height]`

For volumes, use a 2D `Polygon` or `MultiPolygon` as the footprint, and add the lower and upper height limits to the same geometry object as a `vertical_extent` member. The footprint is stored once, and the shape and its heights stay together. A `GeometryCollection` can mix volumes with other shapes, because each member can carry its own `vertical_extent`.

Every record states its coordinate reference system in the required `coordRefSys` field. It applies to all positions in `geometry` and to any `vertical_extent`. Currently the only allowed value is OGC `CRS84h`: longitude and latitude in WGS-84 degrees, with heights in metres above the WGS-84 ellipsoid. Because every record carries its CRS, more CRSs can be added later without making older records ambiguous.

### Point or track position

A track position can include height directly as the third coordinate:

```json
"geometry": {
  "type": "Point",
  "coordinates": [-75.6972, 45.4215, 3200.5]
}
```

This represents:

```text
longitude = -75.6972
latitude  = 45.4215
height    = 3200.5 m
```

### Airspace volume

A volume needs both a lower and an upper height. A normal GeoJSON Polygon cannot represent this by itself, so the UME adds a `vertical_extent` member to the polygon.

```json
"geometry": {
  "type": "Polygon",
  "coordinates": [[ ...2D footprint... ]],
  "vertical_extent": { "lower": 45.0, "upper": 165.0 }
},
"coordRefSys": "http://www.opengis.net/def/crs/OGC/0/CRS84h"
```

In this example, the volume covers the footprint from **45 m to 165 m**. If either limit is omitted, the volume is unbounded in that direction. The validator checks that `lower <= upper` and that a shape with a `vertical_extent` has 2D coordinates.

`vertical_extent` is not part of GeoJSON. This is acceptable because the UME follows GeoJSON practice but is not required to be GeoJSON. When a record is converted to GeoJSON for visualization, the converter drops the member or uses it to build a JSON-FG Prism.

Volumes are not built from 3D coordinates. A polygon with heights on its corners describes a surface, not a solid, and GeoJSON has no solid type. Non-prismatic volumes, such as sloped approach surfaces, can be added later as a separate geometry type or a mesh asset if needed.

### Heights relative to the ground (AGL)

AGL is not a CRS, because it depends on the terrain at each point. Heights are therefore always converted before they are stored:

- **Points:** z = terrain height above the ellipsoid (from a DEM and geoid model) + the AGL value.
- **Volumes:** for a terrain-following limit such as "SFC to 400 ft AGL", `vertical_extent` holds a conservative box that contains the real volume: `lower` = minimum terrain under the footprint + the lower limit, and `upper` = maximum terrain + the upper limit.
- **In both cases** the source value is kept in the payload (`altitude` with `reference: "AGL"` or `"SFC"`), and `vertical_approximate` is set to `true`. Exact terrain-following checks use the payload values and a DEM. The envelope is used for fast filtering.

This keeps every z value comparable across records, so no query needs a terrain lookup.

### Why use this approach?

- **Location and height stay together.** Points and tracks keep their height directly in the geometry instead of using a separate height field.
- **Track positions are simple.** A position is represented as `[longitude, latitude, height]`, which is easy for mapping and 3D clients to work with.
- **One shape, with its heights.** The footprint is stored once, and its height limits sit on the same geometry object, so there is no second copy to keep in sync and no separate field to look up.
- **Easy to index and query.** The ingest step indexes the 2D shape spatially (for example in PostGIS or OpenSearch) and stores `lower` and `upper` as numeric columns. A 3D query becomes "footprint intersects" plus a range check on the heights.
- **Volumes have clear lower and upper limits.** This matches the way UTM volumes, NOTAMs, and geofences are commonly described.
- **The CRS is explicit.** `coordRefSys` on every record says how coordinates and heights should be read, so the CRS can change later without breaking existing data.
- **GeoJSON and JSON-FG are produced downstream.** The UME is internal storage and clients do not need to read it directly. Downstream services convert records to GeoJSON for visualization, and can build a JSON-FG Prism from a polygon and its `vertical_extent` when a client needs one.
